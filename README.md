# Cybercrime Predictive Intelligence Platform

An AI/ML-powered prototype that analyzes cybercrime complaint patterns,
transaction data, time and geographic signals to forecast likely cash
withdrawal hotspots — enabling proactive intervention by law enforcement
agencies (LEAs), coordinated through I4C, and faster fund-blocking
coordination with banks/financial institutions.

Built against the problem statement's four deliverables:

| Deliverable | Where it lives |
|---|---|
| a. Predictive Analytics Engine | `ml/` (training/scoring) + "Predictive Analytics Engine" tab in the dashboard |
| b. Risk Heatmap Dashboard (GIS) | "Risk Heatmap Dashboard" tab (Folium heatmap + hotspot table) |
| c. Law Enforcement Interface | "Law Enforcement Interface" tab (case search + investigator case view) |
| d. Alert & Notification System | "Alerts & Notifications" tab (simulated SMS/Email/API delivery log) |

### Closed-loop validation (SIH mentor requirement)

A mentor round specifically challenged the team on **real-time validation**.
Since the prototype has no live banking/transaction feed, this is answered
with an honest, controlled simulation rather than a fabricated real-time
claim — see the **"Closed-Loop Validation"** tab:

```
PREDICT  →  (simulated) EVENT  →  VALIDATE  →  METRICS
```

1. Enter (or generate) a new complaint — city, crime type, amount, hour.
2. **Generate Prediction** ranks the Top-3 candidate withdrawal locations
   in that city (not a single point guess), each with a confidence score,
   risk level, expected time window, and a short plain-language
   explanation of *why* it was ranked highly.
3. **Simulate Event & Validate** generates a synthetic withdrawal outcome
   — either "Realistic" (weighted by true historical risk) or one of the
   test-case scenarios from the problem statement (Top-1 hit, Top-3 hit,
   geographic near miss, complete miss) — and scores the prediction
   against it: Top-1 hit, Top-3 hit, geographic error (km, haversine),
   time-window hit, and simulated lead time.
4. A running case timeline and aggregate performance metrics (Top-1/Top-3
   accuracy, average geographic error, time-window accuracy) accumulate
   across every case simulated in the session.

This is implemented in `ml/case_predictor.py` (ranked, explainable
predictions) and `ml/validation_engine.py` (event simulation + scoring).
It is explicitly labelled as a controlled simulation — not a claim of
live validation against real banking data.

> **Prototype notice:** all data is synthetic/anonymized, generated by
> `data/generate_data.py`. No real complaint, financial or personal data
> is used. The notification channels shown in the dashboard are simulated
> for demonstration only.

## Project structure

```
data/
  generate_data.py        # synthetic complaint data generator
  cybercrime_data.csv      # generated dataset (6,000 complaints, 12 cities, 62 withdrawal points)
  hotspot_risk_scores.csv  # generated per-location risk scores
ml/
  train_model.py           # trains the RandomForest withdrawal-likelihood classifier
  risk_scoring.py          # aggregates complaints into per-location risk scores
  predict.py                # interactive CLI: score a single case
  hotspot_prediction.py     # quick CLI hotspot report
  final_predictor.py        # CLI: ML probability + location risk combined
  cybercrime_model.pkl       # trained model artifact
dashboard/
  app.py                    # Streamlit dashboard (main deliverable)
requirements.txt
.streamlit/config.toml       # dashboard theme
```

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
```

## Regenerating data & model (optional — pre-built artifacts are included)

```bash
python data/generate_data.py     # regenerate synthetic complaints
python ml/risk_scoring.py        # recompute per-location risk scores
python ml/train_model.py         # retrain the classifier
```

These scripts are path-independent and can be run from any directory.

## Running the dashboard

```bash
streamlit run dashboard/app.py
```

## How the risk model works

1. **Data generation** ties every withdrawal point (`ATM-XXX-NN`,
   `BANK-XXX-NN`, `CSC-XXX-NN`) to real coordinates near an actual city,
   and makes withdrawal likelihood depend on crime type, time-of-day,
   distance, and amount — so both the ML model and the GIS heatmap carry
   real, learnable signal instead of random noise.
2. **`risk_scoring.py`** aggregates historical complaints per withdrawal
   location into a weighted 0–100 risk score (historical withdrawal rate,
   average amount, average distance, complaint volume) and derives each
   location's peak-risk hour.
3. **`train_model.py`** trains a Random Forest classifier on
   `amount`, `complaint_hour`, `withdrawal_hour`, `distance_km` to predict
   the probability that a *new* complaint will end in a cash withdrawal.
4. The dashboard's Predictive Analytics Engine tab uses the trained model
   for single-case scoring; the Risk Heatmap tab uses the aggregated
   location risk scores for GIS visualization; `final_predictor.py` shows
   how the two can be combined to rank the most likely hotspots for a new
   complaint.

## Roadmap to production

- Replace synthetic data with authorized, access-controlled feeds from the
  National Cybercrime Reporting Portal and the Citizen Financial Cyber

  audit logging.
- Wire the Alert & Notification tab to real SMS/email/API gateways.
- Add model monitoring/retraining pipeline as new complaint data arrives.
